# GEN-3「火」— 匿名社会的証明 設計書 v1

- 日付: 2026-08-18 ／ 起案: リード ／ 承認: 勝彦（GEN-3着手指示 2026-08-18・完全自走）
- 位置づけ: GENプログラム第3弾。「このネットワークは生きている・動いている」という事実を、
  匿名の集計値としてパートナーに見せ、次の紹介の火種にする。
- 大原則: **本物の数字だけ**（deals正典=2026-07-26以降すべて実データ・ペルソナの真実ゲート）。
  盛らない・作らない・0を誇張しない。数字が無い週は**黙る**（静音原則）。

## 1. 設計判断（リード裁定）

1. **ネットワーク全体の集計のみ**。個人特定に繋がる粒度（誰が・どの会社・どのメニューで・いくら）は
   構造的に出さない。出してよい軸は「種類（紹介/成約/新メンバー）×件数×期間」だけ。
2. **抑制ルール（コールドスタート対応）**: 値が0の行は出さない。全行0なら面ごと出さない
   （「まだ0件です」を見せない＝空騒ぎ・空虚さの両方を回避）。件数はそのまま出す
   （現在の規模で「1件」が見えるのは望ましい社会的証明であり、誰かは特定できない）。
3. **表示先は2箇所だけ**: ①APPホームの「ネットワークの鼓動」カード ②週次ダイジェストの1行。
   顧客面（/r/）には出さない（顧客への実績訴求は別物・GEN-3のスコープ外）。
4. **金額は一切出さない**（見込み・確定とも）。GEN-1/2と同じ money 境界 assert を適用。
5. **決定的生成・AI不使用**。同じDB状態なら同じ文言。

## 2. 仕様

### 2.1 集計（lib/social-proof.ts + server）
- 対象期間: **直近30日（APPカード）／直近7日（ダイジェスト行）**。JST基準。
- 指標（この3つのみ・すべて実テーブルの count）:
  - `referrals`: deals の新規起票数（throwaway/テスト排除は不要＝正典空以降すべて実物。
    ただし cc-monitor・is_system 系パートナーの行は恒久除外）
  - `wins`: deals の成約遷移数（status が won 系へ確定した件数・期間内）
  - `newPartners`: partners 新規登録数（status=active・is_system=false・内部シンク/cc-monitor除外）
- 実装: 読み取り専用・service-role・`unstable_cache`（revalidate 600s）。money列はselectしない。

### 2.2 APPホーム「ネットワークの鼓動」カード
- 位置: StatCard群の下・やることの上（既存カード文法・0.5px罫線・静音トーン）。
- 文言（例・全行が抑制対象）:
  - 「この30日で、新しい紹介が {referrals}件 動きました」
  - 「{wins}件が成約になりました」
  - 「新しい仲間が {newPartners}人 加わりました」
- 全指標0なら**カード自体を描画しない**（DOMごと不在）。ローディングスケルトンも出さない
  （後追い差し込みでレイアウトシフトを起こさない実装＝サーバ側で有無確定）。
- ⓘ不要（1行文言のみ・知識性なし）。数字はリンクにしない（自分の案件一覧と混同させない）。

### 2.3 週次ダイジェストへの1行（GEN-1連携）
- 差し込み位置: 「あなたの現在地」の直後・「今週のネタ」の前。
- 文言: 「先週、ネットワークでは 新しい紹介が{referrals}件・成約が{wins}件 ありました」
  （0の指標は句ごと省略・両方0なら行ごと省略）。
- 実装: weekly-digest-server が同じ lib/social-proof を使用（生成経路の二重化禁止）。
  既存の money 境界 assert（buildDigestCopy）を通過する（件数のみ＝通る設計）。
- ダイジェストは配信トグル既定OFFのまま＝この行の実配信も勝彦の点火後に始まる。

### 2.4 API
- `/api/app/social-proof`（partner認証・GET のみ・campaign なし）: `{ referrals, wins, newPartners }`。
  APPカードがSSRで直接libを呼べる構成ならAPIは省略可（Codex判断・薄い方を選ぶ）。

## 3. 境界・不変
- money 4ハッシュ非接触（全て読み取り・money列をselectしない）。
- 出力は件数と定型文のみ。パートナー名・社名・顧客名・メニュー名・金額・率の出力経路が存在しない
  ことを型で保証（数値3つ+期間だけを受ける関数シグネチャ）。
- deals/partners への書込なし。既存ダイジェスト文面の他部分は不変。
- 認証・cookie 非接触（APPカードは既存認証内・digestは既存経路）。

## 4. 検証（実装バッチ合格条件）
1. 単体（canon配線）: 抑制ルール全分岐（各指標0/1/複数・全0で空）・決定性・文言にmoney語なしを
   型レベル+テストで証明。
2. throwaway E2E: throwaway partner+deals を作り、30日/7日窓の件数がDB実測と一致→
   全撤去後はカード不在（全0抑制）を実走。既存実データ（高さん系）の件数を変えない読み取り専用証明。
3. APPホーム実ブラウザ: カード出現時の375px溢れ0・全0時にDOM不在・レイアウトシフトなし
   （スケルトン非表示の確認）・pageerror 0。
4. ダイジェスト: 3セグメントのsnapshotに証明行が正しく入る/全0で消えることを suppress下で確認。
   禁止語grep（金額・名前・社名・メニュー名）。
5. ペルソナの真実: 表示数値=SQL直接集計の全桁一致を機械突合。
6. 品質ゲート7項目・test:verify 全green・money 4ハッシュ前後一致・残置ゼロ。
