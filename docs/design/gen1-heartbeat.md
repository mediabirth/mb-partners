# GEN-1「鼓動」— 週次パートナーダイジェスト 設計書 v1

- 日付: 2026-08-13 ／ 起案: リード ／ 承認: 勝彦（GEN-1着手指示 2026-08-13）
- 位置づけ: GENプログラム第1弾（YES定義=2回目紹介率をNorth Starとする「生み出し続ける」化）。
- 原則: pull型製品に**自動のリズム**を与える。送信総量は**1パートナー週1通に固定**。

## 1. 設計判断（リード裁定）

1. **7日ソフトナッジは独立メールにせず、ダイジェストのセグメント別文面に統合**する。
   理由: 送信総量が週1で固定（うるさくならない）・特定電子メール法のオプトアウト管理が1本・実装/検証が1本。
2. **メールに金額は載せない**（件数と状態のみ・金額はアプリで）。転送リスクへの境界安全。
   案件の記述は public-timeline と同じ許可思想＝進行状態のみ。
3. **Phase 1 はメールのみ**（LINE版はGEN-1.5・メール実績を見てから）。
4. **段階解禁**: 実装バッチはプレビュー配信（勝彦＋内部シンク宛）まで。全パートナー本配信は
   console の配信トグル ON をもって開始（勝彦の手で点火）。

## 2. 仕様

### 2.1 配信
- スケジュール: **毎週金曜 11:00 JST**（週末の会食・商談前にネタを持たせる）。vercel cron
  `/api/cron/weekly-digest`（CRON_SECRET必須・無署名401）。
- 対象: `partners.status='active'` かつ メール通知ON（member_notification_prefs.email_enabled
  ／未設定はprofiles.email）。登録3日以内はスキップ（登録直後のメール重複回避）。
  配信停止者（§2.4）除外。cc-monitor系・mb-system.internal宛は恒久除外。
- 送信: lib/email（Resend・ブランドテンプレ・CC_MAIL_SUPPRESS準拠）。mail_log 記録
  （template_key='weekly-digest'）。同一週の再実行は mail_log で冪等スキップ。

### 2.2 文面（セグメント別・自動判定）
共通構造: ①冒頭1行（セグメント別） ②あなたの現在地（進行中N件・直近の動き=状態語のみ・未読M件）
③今週のネタ1つ ④CTA（紹介する／まず相談）⑤配信停止リンク。

| セグメント | 判定 | 冒頭文面の狙い |
|---|---|---|
| 新規未紹介 | 登録後7日以上 かつ 紹介0件 | 「最初の一歩」＝まず相談の提案（7日ナッジの統合先） |
| 進行中あり | 進行中案件≥1 | 現在地の安心＋次の紹介の誘い |
| しばらく静か | 最終起票から21日以上 | 軽いネタ提示（責めない文面・copy-guideline静音準拠） |

### 2.3 「今週のネタ」の選定（決定的アルゴリズム・AI不使用）
1. 今週公開された新着メニューがあれば最優先。
2. なければ 22メニューのローテーション（partner_id+週番号のハッシュで決定的に分散＝
   同じ人に同じネタが連続しない・テスト再現可能）。
3. 体裁: メニュー名＋「こんな人がいたら」（short_description流用）＋ /r/ 直リンク
  （紹介リンクは本人の referral_links を使用・無ければ生成せずアプリ誘導）。
4. リンクには `?src=digest` を付与（ファネル帰属＝2回目紹介率計測の布石）。

### 2.4 配信停止（特定電子メール法対応）
- メールフッターに**ワンクリック配信停止リンク**（署名付きtoken・ログイン不要・押下で
  member_notification_prefs.email_enabled=false・完了画面は静音1行）。
- アプリ内の設定→メール通知OFFでも停止（既存機構と同一のスイッチ＝二重管理しない）。

### 2.5 運営コントロール（console）
- 配信ページに「週次ダイジェスト」節: **配信トグル（既定OFF）**・次回配信のプレビュー
  （対象者数・セグメント内訳・文面サンプル3種）・直近の配信履歴（送信数/停止数）。
- トグルOFF時は cron が何もしない（mail_log にも書かない・完全無音）。

## 3. 境界・不変
- money 4ハッシュ非接触（全て読み取り）。金額・fee系・委託費はメール本文に一切出さない
  （public-timeline許可思想を文面生成に適用・禁止語grepを検証項目化）。
- 送信インフラは既存 lib/email の単一入口（新規経路を作らない）。
- 実ユーザーへの本配信はバッチ内で行わない（トグル既定OFF＋プレビューのみ）。

## 4. 検証（実装バッチ合格条件）
1. suppress下で3セグメントのthrowawayに生成→文面スナップショット（金額・禁止語の非出現grep）。
2. 内部シンク宛に実1通のみ送信して構造確認（件数明示・AGENTS.md規律5）。
3. ワンクリック停止の実走（token→OFF→以後の対象外を機械確認・再有効化は設定から）。
4. 冪等性（同一週2回実行で送信1回）・トグルOFFで完全無音・cron無署名401。
5. ネタ選定の決定性（同partner同週=同ネタ・翌週=別ネタ）単体テスト。
6. 品質ゲート7項目・test:verify 全green・残置ゼロ。

## 5. 点火手順（バッチ後・勝彦の手番）
console→配信→週次ダイジェスト→プレビュー確認→トグルON。初回配信の翌週、
開封に代わる実測として「digest経由の/r/閲覧・起票数」をファネルで確認（GEN計測の初データ）。
